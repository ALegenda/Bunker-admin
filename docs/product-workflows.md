# Product Workflows

## Цель

Этот документ фиксирует целевой UX полноценной версии Bunkeropedia. Он важнее набора отдельных CRUD-страниц: код, маршруты и компоненты должны поддерживать понятный редакционный workflow автора и экспертов.

Bunkeropedia - публичная энциклопедия правил и приватный инструмент правок. Это не игровой движок: приложение не обязано исполнять эффекты карточек, считать фазы игры или автоматически разрешать игровые конфликты.

## Роли пользователей

- Игрок читает опубликованную энциклопедию без авторизации, ищет карточки и разделы правил, открывает постоянные ссылки.
- Эксперт входит через Telegram, читает опубликованную энциклопедию и предлагает правки из контекста карточки или раздела.
- Автор входит через Telegram, управляет черновиком, принимает предложения, публикует версии, импортирует/экспортирует JSON и генерирует PDF.
- Админ управляет пользователями, инвайтами, системными настройками и деплоем. В небольшом проекте автор и админ могут быть одним пользователем.

## Публичная энциклопедия

Главный пользовательский сценарий:

1. Игрок открывает актуальную опубликованную версию.
2. Ищет карточку, правило или термин.
3. Фильтрует карточки по типу, времени, частоте, месту применения и тегам.
4. Открывает карточку или раздел правил.
5. Копирует постоянную ссылку.

Требования к UX:

- Поиск всегда заметен и быстрый.
- Мобильная версия не должна превращать фильтры в препятствие для чтения.
- Карточка показывает тип, атрибуты, описание, упомянутые термины и версию правил.
- Раздел правил имеет якоря для ссылок на конкретные подпункты.
- Публичный UI по умолчанию никогда не показывает draft.

## Рабочий стол автора

`/admin` - не список таблиц, а состояние редакционной работы.

На экране должны быть:

- текущая опубликованная версия;
- активный черновик или действие создания черновика;
- количество измененных карточек и разделов;
- количество предложений по статусам;
- быстрые действия: открыть черновик, открыть предложения, preview, публикация, импорт/экспорт JSON, генерация PDF.

## Редактор черновика

`/admin/workspace` - основной экран автора.

Макет:

- Левая колонка: дерево контента. Верхний уровень: правила, роли/термины, умения, припасы, мертвые бонусы.
- Центральная область: TipTap-редактор выбранного элемента.
- Правая колонка: инспектор выбранного элемента.
- Верхняя панель: активная версия, autosave/save state, preview, diff, publish.

Редактор карточки:

- тип карточки;
- название;
- описание в TipTap;
- время активации;
- частота;
- место применения;
- теги;
- source refs;
- связанные предложения;
- история изменений.

Редактор раздела правил:

- заголовок;
- slug;
- родительский раздел;
- порядок;
- содержимое в TipTap;
- source refs;
- связанные предложения;
- история изменений.

TipTap должен поддерживать структурированный текст: абзацы, списки, таблицы, выделения, ссылки на карточки и ссылки на термины. Произвольный MDX не используется как основной формат.

## Экспертские предложения

Эксперт не должен работать в админке как автор. Его workflow начинается с чтения энциклопедии.

Сценарий правки:

1. Эксперт входит через Telegram по invite flow.
2. Открывает карточку или раздел.
3. Нажимает действие предложения правки.
4. Видит копию текущего текста и редактирует ее.
5. Заполняет комментарий: зачем нужна правка.
6. Видит diff.
7. Отправляет предложение.
8. Отслеживает статус и отвечает на комментарии автора.

Сценарий новой карточки:

1. Эксперт выбирает тип карточки.
2. Заполняет название, описание и доступные атрибуты.
3. Добавляет комментарий и источники, если есть.
4. Отправляет предложение.

Статусы предложения:

- `draft`
- `submitted`
- `in_review`
- `needs_changes`
- `accepted`
- `applied_to_draft`
- `published`
- `rejected`

`accepted` означает, что автор согласен с идеей. `applied_to_draft` означает, что изменение уже внесено в активный черновик. `published` означает, что оно вошло в опубликованную версию.

## Inbox предложений автора

`/admin/proposals` должен быть рабочей очередью, а не просто таблицей.

Группы:

- новые предложения;
- предложения с комментариями экспертов;
- принятые, но не примененные;
- конфликтующие при применении;
- отклоненные;
- опубликованные.

Карточка предложения показывает:

- объект изменения;
- автора предложения;
- базовую версию;
- статус;
- краткое объяснение;
- diff;
- комментарии;
- действие применить к draft, запросить изменения или отклонить.

Если исходный текст изменился после создания предложения, применение должно показывать конфликт.

## Публикация версии

`/admin/versions/:id/publish` - финальный checkpoint.

Перед публикацией автор видит:

- diff draft против последней published;
- changelog человеческим языком;
- добавленные, измененные и удаленные карточки;
- измененные разделы правил;
- примененные предложения;
- validation errors;
- preview публичной энциклопедии;
- возможность сгенерировать PDF preview.

Публикация создает immutable published-версию. Старый published становится archived или остается published в истории, но публичная энциклопедия выбирает последнюю опубликованную версию.

## JSON import/export

`/admin/data` - рабочая поверхность для обмена данными через JSON.

Зачем это нужно:

- выгрузить актуальные правила и карточки в JSON, чтобы отправить в LLM и получить консультацию;
- сохранить переносимый снимок версии;
- импортировать проверенный JSON patch обратно как новый черновик;
- проверить JSON до записи в БД.

Экспорт:

1. Автор выбирает версию: latest published, active draft или конкретную версию из истории.
2. Выбирает режим: `llm_context`, `full_version`, `cards_only`.
3. Видит, какие данные войдут в файл.
4. Скачивает JSON.

`llm_context` должен исключать приватные данные: пользователей, Telegram ids, инвайты, сессии, preview tokens и внутренние security-поля. В него входят только данные, полезные для анализа правил: карточки, разделы, атрибуты, теги, source refs и changelog.

Импорт:

1. Автор загружает JSON.
2. Система валидирует `schemaVersion`, структуру и ссылки между сущностями.
3. Автор видит dry-run: сколько карточек/разделов будет добавлено, изменено, удалено, какие есть ошибки и предупреждения.
4. Если JSON валиден, импорт создает новый draft или применяет изменения к активному draft после явного подтверждения.
5. Published-версия не меняется напрямую.

Для LLM-консультаций предпочтительный экспорт - `llm_context`. Обратно импортируется не сам `llm_context`, а `llm_patch` с явными операциями и `baseVersionId`.

## PDF

PDF генерируется из тех же данных, что и публичная энциклопедия.

Минимальный workflow:

1. Автор выбирает draft или published-версию.
2. Запускает генерацию.
3. Видит статус, дату, checksum и ссылку на файл.
4. Может скачать PDF.

HTML print-шаблон должен максимально повторять существующий PDF-документ по структуре и визуальному стилю. Для production PDF хранится в persistent volume через storage abstraction; метаданные всегда хранятся в PostgreSQL.
