# Аудит данных

## Источники

- `docs/cards.json`: 260 структурированных карточек.
- `Правила Бункер 22.05.26 СЖТ (OCR).pdf`: OCR PDF на 98 страниц, основной источник правил и сверки формулировок.

## Подтвержденные типы карточек

В JSON присутствуют:

- `умение`: 127 карточек.
- `припас`: 84 карточки.
- `мёртвый бонус`: 49 карточек.

В первых страницах PDF также подтверждены общие разделы: введение, вылазка, игра мертвых, дуэль, базовые роли.

## Атрибуты карточек

Текущие справочники:

- Время активации: `дневное`, `ночное`.
- Частота: `одноразовое`, `двухразовое`, `трёхразовое`, `многоразовое`, `пассивное`.
- Место применения: `внутри бункера`, `на вылазке`.
- Теги: сейчас встречаются `Голосование` и `опасная личность`.

Наблюдения по текущему JSON:

- У `мёртвых бонусов` обычно нет `attributes`. Это нормальная особенность типа, а не ошибка импорта.
- Теги есть только у меньшей части карточек: текущий набор тегов недостаточен для хорошего поиска и фильтров.
- Названия не дублируются внутри пары `cardType + name`, но одинаковое название может встречаться у разных типов. Поэтому стабильный идентификатор не должен зависеть только от названия.
- Длинные описания встречаются часто, значит редактор должен поддерживать комфортное чтение, списки, абзацы и структурированное форматирование, а не только textarea.

## Риски данных

- OCR содержит переносы строк, табуляции и вероятные ошибки распознавания. Например, встречаются неточные слова в разделе мертвых бонусов.
- PDF и JSON могут расходиться в формулировках карточек, потому что JSON уже является нормализованным производным источником.
- Не все общие правила безопасно парсить регулярками. Первичная структура разделов создается вручную или полуавтоматически; спорные места лучше оставлять с комментарием в `SourceRef` или решать через обычную редакторскую правку.
- Для карточек пока нет `sourcePage`, потому что надежная связь JSON-карточки со страницей PDF требует отдельной сверки.
- Автоматическое извлечение всех игровых сущностей из PDF не является целью первой реализации. Продукт - энциклопедия и редакционный инструмент, не игровой движок.

## План нормализации

1. Использовать `docs/cards.json` как первичный структурированный импорт карточек.
2. Нормализовать типы, время, частоту, места применения и теги в `AttributeDictionary`.
3. Создавать внутренний стабильный `id`, публичный slug из типа и названия, а при переименовании хранить старые адреса в `SlugAlias`.
4. Сохранять каждую карточку как `Card` + `CardRevision` в published-версии `0.1.0-prototype`.
5. Добавлять разделы правил вручную или полуавтоматически из PDF.
6. Для каждой импортированной карточки создавать `SourceRef` на `docs/cards.json`; `sourcePage` заполнять позже после ручной или полуавтоматической сверки с PDF.
7. Постепенно расширять теги и фасеты поиска через авторский интерфейс, не требуя полной разметки до запуска.
8. Поддерживать обратный экспорт данных из БД в JSON, чтобы актуальную published/draft-версию можно было передать в LLM для консультации.
9. Для LLM использовать отдельный режим `llm_context`, который исключает auth-данные и оставляет только правила, карточки, атрибуты, теги, источники и changelog.
