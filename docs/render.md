# Render: минимальная конфигурация

Рабочий сайт пока размещён на VPS: https://bunker-vdk.ru. Файл `render.yaml`
описывает отдельное окружение для переноса. Создание Blueprint платное;
наличие файла не означает, что сервисы уже созданы или домен переключён.

## Ресурсы и стоимость

Конфигурация для небольшого сообщества (до 100 пользователей), без горизонтального
масштабирования и без изменения архитектуры приложения:

| Ресурс | Конфигурация | В месяц |
| --- | --- | --- |
| Сайт и API | 0,5 CPU, 512 МБ | $7 |
| PDF по расписанию | 1 CPU, 2 ГБ только на время выполнения | от $1 |
| Приватный MinIO | 0,5 CPU, 512 МБ | $7 |
| Диск файлов | 5 ГБ | $1,25 |
| PostgreSQL 17 | 256 МБ, диск 1 ГБ | $6 |
| **Базовая сумма** | | **от $22,25** |

Источник: [Render Pricing](https://render.com/pricing), проверено 18 сентября 2026.
Цена не включает налоги, возможную плату существующего workspace и превышение
лимитов трафика/сборок. На Hobby включены 5 ГБ исходящего трафика и 500 минут сборки;
сверх лимитов действует тарификация Render. Перед созданием проверить тариф и
оставшуюся квоту сервисов в аккаунте. Бесплатная PostgreSQL не предназначена для
постоянного хранения production-данных.

PDF-процесс запускается раз в минуту, обрабатывает очередь и завершается. Поэтому
к ожиданию сборки добавляются до минуты и время запуска контейнера. Render не
запускает одновременно два экземпляра одного cron job. Его оплата — по времени
работы (около $0,00058/мин для 2 ГБ), минимум $1/месяц. Итоговая сумма может быть
выше базовой в зависимости от длительности запусков. Постоянный PDF worker на
таком же тарифе стоил бы $25/месяц. Пробная сборка полного документа при лимите
512 МБ без swap завершилась OOM, поэтому этот лимит для PDF не используется.

Локальная проверка Docker с 1 CPU / 2 ГБ прошла: PDF на 93 страницы (12,3 МБ),
полный цикл проверки 6,2 секунды, пик памяти около 1120 МиБ. Проверены запись в S3,
healthcheck, главная и отказ гостю в доступе к редакторскому API. Это измерение
на тестовой копии исходных данных, а не нагрузочный тест Render или гарантия
времени для будущих документов.

Все компоненты находятся в Singapore. База и MinIO доступны по приватной сети;
доступ PostgreSQL извне запрещён (`ipAllowList: []`). MinIO использует постоянный
диск и отдельного пользователя приложения, которому разрешены только чтение и
запись в bucket `bunker`. Административные реквизиты не передаются приложению.

## Запуск

1. Войти через `render login`. Проверить `render blueprints validate render.yaml
   --output json`: у результата должно быть `valid: true` (одного exit code мало).
2. Создать ресурсы после согласования расходов. Ветка первого развёртывания —
   `codex/render-hosting`. Автодеплой отключён на время переноса, чтобы рабочий VPS
   и кандидат не изменялись одновременно.
3. Задать `PUBLIC_ORIGIN` равным фактическому HTTPS-адресу web-сервиса; перенести
   `TELEGRAM_CLIENT_ID`, `TELEGRAM_CLIENT_SECRET`, `TELEGRAM_ADMIN_IDS` из текущего
   серверного окружения через секреты Render. Не копировать `.env` в репозиторий.
4. MinIO при запуске создаёт приватный bucket и ограниченного пользователя.
   Pre-deploy API выполняет миграции и идемпотентный seed. Worker запускается
   по расписанию. Для контейнера Chromium включён
   `CHROMIUM_NO_SANDBOX=true`, как и в текущем Docker-развёртывании.
5. Проверить `/api/health`, лендинг, каталог, изображения, защищённые маршруты и
   генерацию полного PDF. Для проверки входа на временном домене добавить точные
   origin и `/auth/callback` в Allowed URLs Web Login бота.

`deploy/render/start.sh` формирует S3 URL из hostname приватного сервиса и
запускает с `exec` нужный процесс. `backend/worker-once.ts` использует существующие
блокировки и аренду заданий, закрывает соединения и выходит при пустой очереди.
Увеличение числа карточек или размеров изображений требует повторной проверки
лимита памяти PDF.

## Перенос действующего сайта

Seed содержит исходные карточки, но не пользовательские правки, профили, историю
и выпуски. Для переноса необходимо восстановить актуальный дамп PostgreSQL и
все объекты приватного bucket в **новые** ресурсы. Перед финальным дампом временно
остановить изменения данных на старом сайте, чтобы не потерять записи между
копированием и переключением. Проверить контрольные суммы файлов и количество
карточек/пользователей/выпусков. Восстановленные сессии отозвать.

После проверки копии подключить `bunker-vdk.ru` в Render, заменить `PUBLIC_ORIGIN`
и DNS, проверить HTTPS, Telegram-вход, сохранение карточки и PDF. Не подключать
`www` без продуманного редиректа: приложение принимает только Host основного
origin. Render healthcheck использует один из подключённых custom domains.
Старый VPS оставить доступным для отката. Откат после новых записей на Render
требует обратной синхронизации данных, одного возврата DNS недостаточно.

После переноса настроить автодеплой из принятой основной ветки после CI и внешнюю
резервную копию объектов. PostgreSQL PITR и snapshot диска Render не заменяют
проверенную согласованную резервную копию базы вместе с файлами.

Документация платформы: [Docker](https://render.com/docs/docker),
[workers](https://render.com/docs/background-workers),
[cron jobs](https://render.com/docs/cronjobs),
[Blueprint](https://render.com/docs/blueprint-spec),
[healthchecks](https://render.com/docs/health-checks).
