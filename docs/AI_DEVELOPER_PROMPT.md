# Prompt for Autonomous AI Developer: Bunkeropedia Web App

Ты автономный AI-разработчик уровня senior/fullstack. Твоя задача - на базе текущего проекта `Bunkeropedia` и PDF с правилами авторской игры "Бункер" разработать production-ready web-приложение для автора игры и закрытого круга участников.

Работай долго и автономно: сначала изучай код и правила, затем планируй, реализуй по этапам, покрывай тестами, документируй решения и готовь деплой. Не ограничивайся косметической доработкой текущего статического справочника: текущий проект является прототипом и источником первичных данных.

## 1. Исходный контекст

В репозитории сейчас есть:

- `Правила Бункер 22.05.26 СЖТ (OCR).pdf` - OCR PDF с подробными правилами игры. Это основной источник доменной информации.
- `docs/cards.json` - текущая база карточек в JSON. В каждой карточке есть `cardType`, `name`, `description`, `attributes.activationTime`, `attributes.usageFrequency`, `attributes.usageLocation`, `attributes.tags`.
- Документы в `docs/`, включая `docs/product-workflows.md`, задают целевой UX и редакционные workflow.
- Если в репозитории есть старые `index.html`, `app.js`, `styles.css`, считай их прототипом и источником UX-идей, а не архитектурной основой.

Продукт, который нужно получить:

- Публичный/игровой фронтенд для игроков: интерактивный справочник по актуальным правилам и картам.
- Админка для автора: редактирование структурированных правил, карт, версий, публикаций и генерация PDF.
- Экспертский режим для опытных игроков по инвайтам: предложения правок формулировок и новых карточек без прямой публикации.
- История изменений, сравнение версий и управление актуальной опубликованной версией.
- Импорт и экспорт актуальных данных через JSON, чтобы автор мог передавать снимок правил в LLM для консультации и импортировать проверенные правки обратно в черновик.
- Автоматизированный деплой на VDS с CI/CD.

Bunkeropedia - энциклопедия и редакционный инструмент, а не игровой движок. Не моделируй исполнение эффектов карточек, автоматический расчет фаз игры или разрешение игровых конфликтов, если это не нужно для справочника, редактирования, поиска, версий и PDF.

## 2. Главные продуктовые цели

1. Структурировать правила так, чтобы обновления не требовали ручной правки PDF, Word-файла и статического JSON.
2. Сделать единый источник правды: актуальные правила редактируются в приложении, а справочник и PDF генерируются из данных.
3. Поддержать версии правил: черновики, публикации, changelog, сравнение с предыдущей версией, откат при необходимости.
4. Дать закрытому сообществу возможность предлагать изменения, но оставить финальное утверждение автору.
5. Поддержать переносимый JSON-снимок данных для LLM-консультаций, аудита и резервного обмена данными.
6. Получить приложение, которое можно развернуть на VDS и поддерживать без ручной сборки на сервере.

## 3. Рекомендуемый стек

Если в репозитории нет уже выбранного fullstack-стека, используй следующий консервативный стек:

- TypeScript.
- Next.js App Router как единое fullstack-приложение.
- PostgreSQL для данных.
- Prisma ORM для схемы, миграций и seed.
- Telegram Login Widget как основной способ входа для автора и экспертов.
- Tailwind CSS и, при необходимости, shadcn/ui для админского интерфейса.
- TipTap/ProseMirror для rich text правил и карточек.
- Playwright для генерации PDF из HTML-шаблона.
- Docker Compose для VDS: app, postgres, Caddy, optional backup job.
- GitHub Actions для CI/CD.

Если выбираешь другой стек, зафиксируй причину в `docs/architecture.md` и убедись, что он закрывает те же требования.

## 4. Доменная модель

Перед реализацией внимательно прочитай PDF, `docs/cards.json`, `docs/data-audit.md` и `docs/product-workflows.md`. Выдели сущности, которые реально нужны энциклопедии и редакционному workflow. Минимальная модель должна покрывать:

- `Rulebook` - набор правил/издание игры.
- `RulebookVersion` - конкретная версия правил: draft, review, published, archived.
- `RuleSection` - структурированный раздел правил с порядком, заголовком, slug, контентом и вложенностью.
- `Card` - карточка как стабильная сущность: внутренний id, публичный slug, тип, название, статус, теги.
- `CardRevision` - версия текста и атрибутов карточки в конкретной версии правил.
- `CardType` - на текущих данных минимум `умение`, `припас`, `мёртвый бонус`. Роли, наемники и другие сущности добавляй как отдельные типы карточек только если они действительно нужны для энциклопедии, а не просто встречаются в PDF.
- `AttributeDictionary` - справочники атрибутов: время активации, частота, место применения, категории/теги.
- `GlossaryTerm` - игровые понятия: вылазка, дуэль, лидер, опасная личность и другие термины.
- `SourceRef` - связь карточки/раздела/ревизии с источником: файл, страница PDF, тип источника, комментарий, confidence.
- `SlugAlias` - старые публичные адреса после переименований карточек и разделов.
- `ReviewStatus` или `ReviewTask` - вычитка OCR/JSON: needs_review, reviewing, verified, has_issues.
- `ChangeSet` или `Revision` - атомарный набор изменений с автором, описанием, временем и связью с версией.
- `Proposal` - предложение изменения от приглашенного игрока.
- `ProposalComment` - обсуждение предложения.
- `Invite` - инвайты в закрытую админку.
- `User` и `Role` - автор/админ, редактор, эксперт, читатель.
- `GeneratedPdf` - сохраненная информация о сгенерированном PDF: версия, файл/объект, дата, checksum.
- `DataSnapshot` или `JsonExport` - метаданные JSON-импорта/экспорта: версия правил, режим, schemaVersion, автор, дата, checksum.

Важные инварианты:

- Опубликованная версия правил неизменяемая. Любые правки идут в новый черновик.
- Публичный справочник всегда читает только опубликованную версию, если явно не открыт preview.
- Предложения игроков не меняют опубликованные данные напрямую.
- У карточек должен быть стабильный внутренний идентификатор, публичный slug и история slug-алиасов, чтобы ссылки не ломались между версиями.
- `accepted` и `applied_to_draft` для предложений - разные состояния.
- Мертвые бонусы могут не иметь стандартных атрибутов времени/частоты/места.
- JSON-импорт не меняет published-версию напрямую. Он создает новый draft, применяет изменения к active draft или показывает dry-run diff.
- JSON-экспорт для LLM не содержит auth-данных, email пользователей, инвайтов, сессий, паролей, preview tokens и секретов.
- История изменений должна позволять понять, кто, когда и зачем изменил текст.

## 5. Функциональные требования

### 5.1 Игровой фронтенд

Реализуй современную версию текущей "Бункеропедии":

- Поиск по карточкам и разделам правил.
- Фильтры по типу карты, времени активации, частоте, месту применения, тегам.
- Страница карточки с постоянной ссылкой.
- Страница раздела правил с якорями.
- Навигация по опубликованной версии правил.
- Индикатор текущей версии и дата публикации.
- Адаптивный интерфейс для телефона.
- Быстрая загрузка и SEO-friendly страницы, насколько это возможно для закрытого/полузакрытого продукта.

### 5.2 Админка автора

Реализуй закрытую админку:

- Авторизация.
- Рабочий стол версии: опубликованная версия, активный черновик, изменения, предложения, задачи вычитки.
- Основной редактор черновика: дерево контента, редактор выбранного элемента, инспектор атрибутов/источников/проверок.
- Редактирование разделов правил.
- Редактирование карточек и их атрибутов.
- Управление порядком разделов и карточек.
- Черновики и публикация новой версии.
- Просмотр истории изменений.
- Сравнение текущего черновика с последней опубликованной версией.
- Подсветка добавленных, удаленных и измененных фрагментов текста.
- Preview публичного справочника для черновика.
- Режим вычитки OCR/JSON и спорных мест.
- Импорт и экспорт JSON-снимков данных.
- Генерация PDF для черновика и опубликованной версии.
- Управление пользователями и инвайтами.

### 5.3 Ограниченная админка для экспертов

Опытные игроки по инвайтам должны иметь ограниченный доступ:

- Принять инвайт и создать аккаунт.
- Просматривать актуальные правила и карточки.
- Предложить правку текста карточки или раздела правил.
- Предложить новую карточку с типом, названием, описанием и атрибутами.
- Видеть статус своих предложений: draft, submitted, in_review, needs_changes, accepted, applied_to_draft, published, rejected.
- Комментировать обсуждение своего предложения.

Автор/админ должен иметь возможность:

- Просматривать очередь предложений.
- Смотреть diff предложения относительно текущей версии.
- Оставлять комментарии.
- Принять предложение целиком.
- Принять предложение с правками.
- Отклонить предложение с причиной.
- Включить принятые предложения в черновик следующей версии.

### 5.4 Версионирование

Реализуй workflow:

1. Есть последняя опубликованная версия.
2. Админ создает новый черновик на ее основе.
3. В черновике редактируются правила и карточки.
4. Принятые предложения экспертов могут быть применены к черновику.
5. Перед публикацией админ видит changelog и diff.
6. После публикации черновик становится immutable published-версией.
7. Публичный фронтенд начинает читать новую опубликованную версию.

Нужно уметь сравнить:

- Версия N против N-1.
- Черновик против последней публикации.
- Предложение эксперта против текущего текста.

### 5.5 PDF

PDF должен генерироваться из тех же структурированных данных, что и сайт.

Минимальные требования:

- Титульная страница.
- Оглавление.
- Разделы общих правил.
- Разделы карточек по типам.
- Единый стиль, подходящий для печати.
- Номер версии и дата генерации.
- Повторяемый результат: один и тот же набор данных должен давать одинаковый содержательный PDF.

Для генерации предпочтительно сделать HTML print-шаблон и рендерить его через Playwright/Puppeteer. Храни информацию о сгенерированном PDF в базе, а сам файл - локально на сервере или в S3-compatible storage, если это будет проще и надежнее.

### 5.6 JSON import/export

Реализуй импорт и экспорт актуальных данных через JSON.

Экспорт:

- Выбор версии: latest published, active draft или конкретная версия.
- Режим `llm_context`: компактный и безопасный файл для передачи в LLM. Включает карточки, разделы правил, термины, атрибуты, теги, источники и changelog. Исключает пользователей, email, инвайты, сессии, пароли, preview tokens и секреты.
- Режим `full_version`: полный переносимый снимок выбранной версии без auth-данных.
- Режим `cards_only`: карточки в формате, близком к `docs/cards.json`.
- Детерминированный порядок ключей и массивов, чтобы JSON было удобно diff-ить.

Импорт:

- Валидация через общие Zod-схемы.
- Dry-run без записи в БД: статистика, ошибки, предупреждения и diff.
- Импорт `docs/cards.json` как seed.
- Импорт `full_version` или `llm_context` только в новый draft или active draft после явного подтверждения.
- Published-версии не меняются напрямую.

Ошибки импорта должны быть понятными: путь в JSON, причина, критичность и возможное действие.

## 6. Нефункциональные требования

- Все новые приложение и серверный код пишутся на TypeScript.
- Валидация входных данных обязательна: Zod или аналог.
- JSON import/export должен использовать общие схемы валидации, чтобы экспортируемый файл можно было импортировать обратно без ручной правки.
- Доступы проверяются на сервере, а не только в UI.
- Секреты не коммитятся.
- Миграции базы воспроизводимы.
- Seed-данные должны позволять локально поднять проект и увидеть импортированные карточки.
- Все важные пользовательские сценарии покрываются тестами.
- Логи должны помогать разбирать ошибки деплоя, генерации PDF и публикации версий.
- UI должен быть понятен русскоязычной аудитории.

## 7. Этапы работы

### Этап 0. Инвентаризация

Цель: понять текущие данные и подготовить план миграции.

Сделай:

- Прочитай PDF и `docs/cards.json`.
- Определи типы контента: общие правила, роли, умения, припасы, мертвые бонусы, наемники и прочие подтвержденные разделы.
- Сравни PDF и `docs/cards.json`: какие поля уже есть, чего не хватает, где есть OCR-ошибки.
- Опиши в `docs/data-audit.md` найденные сущности, проблемы данных и план нормализации.

Готово, когда:

- Есть документ с моделью данных и рисками.
- Понятно, какие данные можно импортировать автоматически, а какие потребуют ручной вычитки.

### Этап 1. Bootstrap fullstack-приложения

Цель: заменить статический прототип на поддерживаемое приложение.

Сделай:

- Инициализируй Next.js + TypeScript, не удаляя исходные файлы без необходимости.
- Настрой ESLint, Prettier, тестовый фреймворк.
- Подключи PostgreSQL и Prisma.
- Создай базовую схему БД.
- Добавь Docker Compose для локальной разработки.
- Добавь `README.md` с командами запуска.

Готово, когда:

- `npm install`, `npm run dev`, `npm test`, `npm run lint` работают локально.
- База поднимается через Docker Compose.
- Миграции применяются с нуля.

### Этап 2. Импорт данных

Цель: перенести текущий `docs/cards.json` в новую структуру.

Сделай:

- Напиши idempotent import script для `docs/cards.json`.
- Нормализуй card types, activation times, usage frequencies, locations и tags.
- Генерируй стабильные внутренние id, публичные slugs и подготовь модель `SlugAlias`.
- Подготовь общую JSON-схему для seed/import/export.
- Создай первую draft/published-версию на основе текущих данных.
- Добавь seed-пользователя админа для локальной разработки через env-переменные.

Готово, когда:

- Свежая база после seed содержит карточки из `docs/cards.json`.
- Повторный запуск импорта не создает дубликаты.
- Экспорт `cards_only` может выгрузить карточки обратно в JSON.
- Публичный справочник может читать данные из БД, а не из статического JSON.

### Этап 3. Публичный справочник

Цель: восстановить и улучшить текущий пользовательский опыт.

Сделай:

- Реализуй главную страницу справочника.
- Реализуй страницы карточек.
- Реализуй поиск и фильтры.
- Реализуй страницы разделов правил.
- Добавь переключение/отображение опубликованной версии.
- Поддержи мобильную верстку.

Готово, когда:

- Основные возможности старого `index.html`/`app.js` доступны в новом UI.
- Ссылки на карточки стабильны.
- Данные берутся из published-версии.

### Этап 4. Авторизация и роли

Цель: закрыть админские возможности.

Сделай:

- Реализуй вход пользователя.
- Реализуй роли: admin/author, expert, viewer.
- Реализуй server-side access control.
- Реализуй инвайты для экспертов.
- Добавь страницы управления пользователями и инвайтами для админа.

Готово, когда:

- Незалогиненный пользователь не может попасть в админку.
- Expert не может публиковать версии и менять данные напрямую.
- Admin может создавать и отзывать инвайты.

### Этап 5. Админка правил и карточек

Цель: сделать приложение главным инструментом редактирования правил.

Сделай:

- Рабочий стол автора `/admin`: состояние published/draft, изменения, предложения, задачи вычитки.
- Основной редактор `/admin/workspace`: дерево контента, редактор, инспектор.
- Редактирование карточек.
- Редактирование разделов правил.
- Редактирование атрибутов карточек.
- Управление порядком.
- Draft workflow.
- Режим вычитки `/admin/review` для OCR/JSON и спорных мест.
- Autosave или явное сохранение с понятными статусами.
- Preview изменений перед публикацией.

Готово, когда:

- Админ может создать черновик новой версии, изменить карточку/раздел и увидеть preview.
- Последняя опубликованная версия остается неизменной.
- Автору не нужно переходить между разрозненными CRUD-таблицами для обычной редакционной работы.

### Этап 6. Версионирование и diff

Цель: сделать изменения прозрачными.

Сделай:

- Историю изменений по карточке, разделу и версии.
- Diff текстов и атрибутов.
- Changelog версии.
- Сравнение draft vs published и published N vs N-1.
- Публикацию версии.

Готово, когда:

- Перед публикацией видно, что изменится.
- После публикации можно открыть страницу "Что изменилось".
- Можно посмотреть историю конкретной карточки.

### Этап 7. Предложения экспертов

Цель: подключить закрытое сообщество к развитию правил.

Сделай:

- UI для создания предложения правки существующей карточки/раздела.
- UI для предложения новой карточки.
- Очередь модерации для админа.
- Комментарии к предложениям.
- Принятие/отклонение предложений.
- Применение accepted-предложения к черновику.

Готово, когда:

- Expert может отправить предложение, но не может изменить published/draft напрямую.
- Admin видит diff предложения и может применить его.
- Статусы предложений меняются прозрачно.

### Этап 8. PDF-генерация

Цель: получать актуальный PDF без ручной сборки.

Сделай:

- HTML print-шаблон правил.
- Генерацию PDF для выбранной версии.
- Сохранение файла и метаданных.
- Кнопку генерации/скачивания в админке.
- Публичную или закрытую ссылку на PDF актуальной версии, в зависимости от выбранной модели доступа.

Готово, когда:

- PDF генерируется из базы.
- В PDF есть версия, дата, оглавление и карточки.
- Генерация покрыта тестом или smoke-тестом.

### Этап 8.5. JSON import/export

Цель: дать автору безопасный обмен актуальными данными через JSON.

Сделай:

- Страницу `/admin/data`.
- Экспорт `llm_context`, `full_version`, `cards_only`.
- Импорт JSON с dry-run.
- Создание нового draft из импортированного snapshot.
- Применение валидного импорта к active draft после подтверждения.
- Метаданные `DataSnapshot` или `JsonExport`: автор, дата, режим, версия, checksum.

Готово, когда:

- Автор может скачать актуальную published/draft-версию в JSON для LLM.
- LLM-export не содержит приватных auth-данных.
- Импорт показывает diff до записи.
- Импорт не может изменить published напрямую.
- Экспортированный `full_version` проходит импортную валидацию.

## 8. Тест-план

Минимальный набор тестов:

- Unit-тесты:
  - slug generation;
  - нормализация импортируемых карточек;
  - validation schemas;
  - diff-функции;
  - JSON export serialization;
  - JSON import validation;
  - permission helpers.
- Integration-тесты:
  - import `docs/cards.json` idempotency;
  - создание черновика из published-версии;
  - публикация версии;
  - accepted proposal не меняет draft до явного применения;
  - applied_to_draft proposal применяет изменения только к draft;
  - export `llm_context` не содержит auth-данных;
  - import snapshot создает draft и не меняет published;
  - expert не может вызвать admin-only mutation.
- E2E-тесты:
  - игрок ищет карточку и открывает ее страницу;
  - админ создает черновик, меняет карточку и публикует версию;
  - эксперт принимает инвайт и отправляет предложение;
  - админ принимает предложение и видит его в changelog;
  - админ экспортирует JSON для LLM;
  - админ импортирует JSON через dry-run в draft;
  - админ генерирует PDF.
- Smoke-тесты деплоя:
  - `/health` отвечает 200;
  - главная страница открывается;
  - login page открывается;
  - published-версия доступна;
  - PDF endpoint не падает.

Перед каждым крупным завершением запускай:

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

Если команда отсутствует - добавь ее или объясни в документации, почему она не нужна.

## 9. Данные и миграция из PDF

Не пытайся сразу идеально распарсить весь OCR PDF регулярками. Действуй прагматично:

1. Используй `docs/cards.json` как первый структурированный источник карточек.
2. PDF используй для сверки разделов, правил, пропущенных сущностей и OCR-проблем.
3. Для общих правил создай первичную структуру разделов вручную или полуавтоматически.
4. Все сомнительные места помечай статусом `needs_review` или `has_issues`.
5. Добавь админский фильтр "требует проверки", чтобы автор мог постепенно вычитать данные.
6. Добавь экспорт актуальной версии из БД обратно в JSON, чтобы автор мог передавать данные в LLM для консультации.

Для импортированных данных сохраняй происхождение:

- `sourceFile`
- `sourceVersion`
- `sourcePage`, если удается определить
- `importedAt`
- `reviewStatus`

Для JSON-экспорта сохраняй:

- `schemaVersion`
- `exportedAt`
- `exportMode`
- `rulebookVersion`
- `checksum`

## 10. UX ориентиры

Перед проектированием экранов прочитай `docs/product-workflows.md` и следуй описанным там рабочим сценариям. Особое внимание удели админке: она должна быть редакционным рабочим местом автора, а не набором CRUD-страниц.

Публичная часть:

- Быстрая, темная, удобная на телефоне.
- Поиск должен быть центральной функцией.
- Карточку должно быть легко отправить ссылкой.
- Фильтры не должны мешать чтению.
- Карточки с длинными описаниями должны удобно читаться и на телефоне, и на десктопе.

Админка:

- Не перегружать автора техническими терминами.
- Основной экран редактирования: дерево контента, редактор и инспектор.
- Всегда показывать, в какой версии работает автор: published, draft или preview.
- Перед публикацией явно показывать последствия.
- Опасные действия подтверждать.
- Историю изменений показывать человеческим языком.
- Встроить отдельный режим вычитки для OCR/JSON, а не прятать его в обычных фильтрах таблицы.
- Для JSON import/export сделать понятный экран: выбор версии, режим экспорта, предупреждение о приватных данных, dry-run импорта и diff перед применением.

Экспертская часть:

- Сделать отправку предложения проще, чем написание сообщения в чат.
- Эксперт предлагает правку из контекста чтения карточки или раздела, а не через отдельную "мини-админку".
- Всегда показывать, к какой версии относится предложение.
- Не давать пользователю ощущение, что его правка уже опубликована.
- Разделять статусы `accepted`, `applied_to_draft` и `published`.

## 11. Безопасность

Обязательно:

- Хешировать пароли, если используется email/password auth.
- Использовать CSRF/session protection согласно выбранному auth-решению.
- Проверять права на сервере для всех mutations.
- Rate limit для login и invite acceptance.
- Не раскрывать draft-версии публично без специального preview token.
- Не хранить секреты в репозитории.
- Подготовить `.env.example`.

## 13. Definition of Done

Проект считается готовым, когда:

- Приложение поднимается локально одной понятной командой.
- Карточки из текущего `docs/cards.json` импортированы в БД.
- Есть опубликованная версия правил.
- Игроки могут пользоваться справочником в браузере.
- Автор может работать в редакционном workspace, редактировать черновик, видеть diff и публиковать новую версию.
- Автор может вычитывать OCR/JSON через отдельный review workflow.
- Эксперты могут заходить по инвайтам и предлагать правки из контекста энциклопедии.
- PDF генерируется из актуальных данных.
- Актуальная версия экспортируется в JSON для LLM-консультаций.
- JSON можно импортировать обратно только через draft и dry-run.
- CI прогоняет lint, typecheck, tests и build.
- CD разворачивает приложение на VDS по SSH.
- Есть backup базы и инструкция восстановления.
- Нет известных критических проблем безопасности.

## 14. Рабочий стиль

- Не делай большие неосмысленные переписывания без причины.
- Если меняешь архитектурное решение, фиксируй почему.
- После каждого этапа оставляй короткий отчет: что сделано, какие команды прошли, какие риски остались.
- Если находишь противоречия в правилах или OCR-ошибки, не выдумывай истину. Помечай данные как `needs_review` или `has_issues` и продолжай.
- Приоритет: сначала надежный сквозной продукт, затем полировка.
- Не коммить секреты, дампы базы, приватные ключи и production `.env`.
