# Развёртывание и Telegram

Рабочий сайт https://bunker-vdk.ru размещён на VPS Hoster.kz в Астане:
`/` — лендинг, `/catalog` — опубликованный каталог, `/admin` — редактор,
`/proposals` — предложения, `/users` — управление доступом. Telegram-вход
настроен. Актуальные адреса, обновление и резервные копии описаны в
[инструкции для Hoster](deployment.md). Ниже — общая настройка новой установки;
не заменяйте ею существующие секреты и Compose рабочего сайта.

## Telegram для новой установки

Используется бот **@bunker_vdk_bot**. Покупка собственного домена не обязательна: подойдёт постоянный HTTPS-адрес, выданный хостингом, или бесплатное DNS-имя для вашего сервера. Нужен хостинг, поддерживающий серверное приложение, PostgreSQL и S3; статического хостинга для всей системы недостаточно. Не стоит подключать временный туннель к режиму локального администратора.

В BotFather откройте настройки входа для этого бота (Web Login). Зарегистрируйте точный origin сайта и URL возврата `https://ВАШ-АДРЕС/auth/callback` в Allowed URLs. Получите **Client ID и Client Secret**. Это отдельные OIDC-реквизиты, обычный Bot API token здесь не используется. Секрет храните в `.env` сервера или в секретах хостинга, не в чате и не в Git.

Официальная инструкция: https://core.telegram.org/bots/telegram-login

```dotenv
NODE_ENV=production
AUTH_MODE=telegram
PUBLIC_ORIGIN=https://ВАШ-АДРЕС
TELEGRAM_CLIENT_ID=значение_из_BotFather
TELEGRAM_CLIENT_SECRET=секрет_из_BotFather
TELEGRAM_ADMIN_IDS=ВАШ_ЧИСЛОВОЙ_TELEGRAM_ID
```

`TELEGRAM_ADMIN_IDS` задаёт администраторов **при первом входе**. Значение — ID личного Telegram-аккаунта, не username и не ID бота. Оно не возвращает права ранее пониженному пользователю. Остальные пользователи получают роль `player`. После их входа администратор выдаёт права на странице «Доступ». При изменении роли сессии пользователя отзываются, он входит заново. Последнего действующего администратора нельзя отключить через интерфейс.

Запуск `NODE_ENV=production` без Telegram-настроек или с HTTP origin завершается ошибкой. В production нет переключателя ролей и локального входа. В разработке `/admin` позволяет явно открыть локальную сессию; гостям права администратора автоматически не выдаются.

## Запуск новой установки

1. Сохраните резервную копию текущего проекта и данных.
2. Настройте `.env`, постоянные тома, HTTPS-прокси и OIDC-реквизиты.
3. Соберите и запустите инфраструктуру и приложение:

```sh
docker compose up -d postgres minio
# Только для пустой новой базы:
docker compose --profile app build
# Сохраняет ручные правки, применяет одноразовые миграции исходных карточек:
docker compose --profile app run --rm api node dist/backend/db/seed.js
# Рабочий режим:
docker compose -f compose.yaml -f compose.production.yaml --profile app up -d --build
```

Миграции применяются API при старте, проверяют контрольные суммы и защищены блокировкой. При первом развёртывании миграции и импорт выполняются до запуска воркера. В дальнейшем воркер пережидает недоступность БД при перезапуске.

В этом примере API слушает только `127.0.0.1:4173` хоста; действующий Hoster-стек использует `127.0.0.1:4174`. Прокси передаёт исходный Host, равный PUBLIC_ORIGIN. Пример для Caddy находится в `deploy/Caddyfile.example`; активная конфигурация Hoster — `/etc/caddy/Caddyfile`. Не открывайте порты PostgreSQL/MinIO наружу.

API и воркер работают от пользователя `node`, с файловой системой только для чтения, временным томом, ограничениями памяти/процессов и удалёнными Linux capabilities. Chromium запускается без собственного sandbox внутри изолированного PDF-контейнера; пользовательский HTML не исполняется, все карточки экранируются, ресурсы документа встроены. Не используйте этот обработчик как произвольный браузер или конвертер чужого HTML.

## Учётные данные хранилища

Локальная установка использует начальные реквизиты MinIO для простоты запуска. На хостинге создайте отдельный S3 access key с доступом только к bucket проекта: чтение/запись объектов и просмотр bucket. Заранее создайте приватный bucket и укажите отдельные реквизиты приложения в `S3_ACCESS_KEY/S3_SECRET_KEY`. Не выдавайте приложению административные ключи облачного аккаунта. Root-реквизиты самостоятельно размещённого MinIO должны быть отдельными (переменные `MINIO_ROOT_USER/MINIO_ROOT_PASSWORD` в Compose).

## Резервные копии и восстановление

`npm run backup` запускается на хосте с Node.js, Docker CLI и `.env`, доступом к PostgreSQL и S3. Он сохраняет дамп БД и объекты с контрольными суммами в `tmp/backups/<дата>`. В дампе также находятся предложения, история и пользователи. Доступ к папке ограничен владельцем.

На рабочем VPS включён `bunker-hoster-backup.timer`, запускающий `/opt/bunker-production/backup.sh`; подробности в [deployment.md](deployment.md). Шаблоны `deploy/bunker-backup.service` и `.timer` относятся к другим установкам и не описывают действующий Hoster-стек. Переносите свежие копии вне сервера; копия на том же диске не защищает от его потери. Автоматическое удаление рабочих копий не включено.

Восстановление: создайте пустую отдельную БД, восстановите `database.dump` через `pg_restore --no-owner --exit-on-error`, проверьте контрольные суммы объектов из `manifest.json`, загрузите `objects/<ключ>` в приватный bucket под теми же ключами. Затем переключите DATABASE_URL и S3-настройки. Не восстанавливайте поверх рабочей базы. После восстановления отзовите все восстановленные сессии (`DELETE FROM sessions`) и начните вход заново. Пароли и OIDC secret не входят в backup, храните их отдельно.

## Наблюдение и границы

`GET /api/health` проверяет PostgreSQL и S3; сессия не нужна. Логи API содержат request ID, путь без query string, статус и время запроса. Cookie и заголовки авторизации скрыты. Воркер пишет результат сборки; очередь хранится в БД, задания с просроченной арендой повторяются не более трёх раз. Для внешнего мониторинга настройте уведомления о 5xx, неуспешных backup и долгих заданиях PDF в вашей системе мониторинга.

Развёртывание рассчитано на один API-процесс и отдельный PDF-воркер. Ограничение частоты запросов находится в памяти API; при горизонтальном масштабировании понадобится общий rate-limit store или ограничитель на ingress. Для каталога этого размера фильтрация выполняется в браузере; при существенном росте объёма потребуется серверная пагинация.

Проверки CI выполняются в `.github/workflows/check.yml`. После изменения настройки Telegram проверяйте вход администратора и игрока, повышение прав, выход и отзыв доступа на рабочем адресе. Локально проверяются подпись токена, issuer/audience/expiry, CSRF и разграничение прав; эти тесты не заменяют проверку реального входа.
